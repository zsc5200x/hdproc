## 4. 优化规划（按优先级）

### P0：优先降低真失败（直接对 21.89% 生效）

1) **降低“盘口已变化→找不到目标盘口线”（76.60%）**
- **缩短分单总耗时**：优先调整 `app/data/follow_settings.json`：
  - `split_delay_seconds` 从 1.0 下调（建议先试 0.2~0.5），减少后续分单赶不上变盘
  - 针对波动大的订单（尤其滚球/临场）：考虑降低 `split_count`（或做“动态 split_count”），优先保证“跟全”
- **降低入队到下注的延迟**：减少排队/串行等待，避免“第 4/5 单时盘口已变”
- **谨慎扩展 line mapping**（需要业务确认能接受的偏差范围）：
  - 增加候选盘口线覆盖面/策略（可能降低失败，但也可能引入“跟到不同盘口线”的风险）

2) **降低“赛事已下架/列表不同步”（11.17%）**
- 对 `gid 找不到` 的订单尽快终止并记录（避免无意义等待）
- 优化抓单 → 跟单触发链路的延迟，减少赛事状态变化窗口

3) **降低“比分已变化（滚球护栏）”（9.57%）**
- 若业务允许“容忍比分变化”则需要明确规则（通常不建议随意放行）
- 若不允许：同 P0-1 的“缩短分单耗时”是最有效手段

4) **消灭“下注金额超过最大投注”（2.13%）**
- 在下注前基于 `order_view_head.gold_gmax` 做更严格的分单/单笔限额校验（必要时增加分单数，而不是硬打导致失败）
- 注意：不同会员的 `gold_gmax` 可能不同，若分单随机会员，需要用“最小 gmax”作为约束或按会员选单

### P1：降低过程报错/重试次数（提高吞吐与稳定性，不直接等同于真失败）

- **把 1X016 按 1X015 同类处理**：遇到 1X016 时也走“快速刷新 + 立即重试”（目前多为泛化“拒绝下注”）
- **优化 1X001（封盘/暂停）策略**：尽量用“探测/等待”替代频繁下注请求，减少噪声与无效重试
- **监控建议（每日对比）**：
  - 真失败率（FAIL_FINAL / stake_orders）
  - 真失败完成度分布（0/5、1/5…）
  - 每单平均重试次数、1X015/1X016/1X001 每单出现次数（看是否被重试放大）
