# 跟单引擎性能瓶颈深度分析与优化方案

> 分析时间：2026-02-06
> 分析对象：follow_engine.py (263KB, 6000+ 行)
> 目标：找出"为什么有些单没跟上拖慢整个队伍"的根本原因

---

## 🔍 一、核心问题总结

经过深入代码分析，发现**真正拖慢整个队伍的核心原因**有以下5个：

### 1. 分单延迟过长（最严重）⚠️

**当前配置：**
```json
"split_delay_seconds": 120.0  // 每笔分单之间等待120秒！
```

**问题：**
- 分3单，需要等待 2 × 120 = **240秒**（4分钟）才能全部完成
- 在这4分钟内，后续所有订单都被阻塞
- 滚球场景下，4分钟盘口早已变化多次

**数据证明：**
从《跟单报错统计与优化方案.md》可知：
- 真失败中 **66%+ 是"已经打出部分分单但没跟全"**
- 核心矛盾是"**分单耗时 + 盘口/比分快速变化**"

---

### 2. 串行队列处理（架构问题）

**代码位置：** `follow_engine.py:5210-5222`

```python
# 每轮循环最多处理 queue_max_per_tick 个订单（默认3个）
queue_max_per_tick = int(settings.get("queue_max_per_tick") or 3)

for job in ready_jobs:
    if processed >= queue_max_per_tick:
        break
    # 串行处理每个job...
```

**问题：**
- **单线程串行处理**队列
- 一个订单卡住（等待盘口、网络慢），后面所有订单都要等
- 例如：订单A在等120秒分单延迟时，订单B、C、D都无法开始

**表现：**
用户看到的现象就是"**像停止了/很久没动**"

---

### 3. 盘口线查找逻辑过于复杂（耗时累加）

**代码位置：** `follow_engine.py:3945-4010`

**查找链路：**
```
1. order_view (预校验，获取当前盘口线)
   ↓ 盘口线不匹配
2. try_refresh_handicap_odds_via_game_more (让球盘)
   - 调用 fetch_game_list_game_context (获取 lid/ecid)
   - 调用 member_warmup_menu (预热菜单)
   - 调用 fetch_game_more_game (获取附加盘盘口)
   - 遍历多个 showtype: live → hot → today → early
   - 遍历多个 wtype: R → AR → BR → CR → DR → ER → FR → RE
   ↓ 还找不到
3. try_refresh_total_odds_via_game_list (大小盘)
   - 调用 fetch_game_list_game (获取赛事列表)
   - 遍历所有盘口线，查找匹配的
   ↓ 还找不到
4. try_refresh_total_odds_via_game_list_p3type (切换板块)
   - 调用 fetch_page_count (获取可用板块)
   - 遍历多个 p3type: MOUA → RNOU → MAIN
   - 每个 p3type 下重新调用 get_game_list
   ↓ 还找不到
5. try_refresh_total_odds_via_game_more (兜底)
   - 再次调用 game_more
```

**单次查找可能调用的接口数量：**
- `order_view`: 1次
- `right_menu / sport_menu / order`: 3次（预热）
- `get_game_list`: 4-8次（多个showtype/p3type组合）
- `get_game_more`: 2-4次（多个showtype/filter组合）
- `get_page_count`: 1次

**总耗时估算：**
- 每个接口 0.5-2 秒（网络延迟 + 服务端处理）
- 总耗时：**10-30 秒**
- 这期间队列被阻塞，后续订单全部等待

---

### 4. 使用历史水位提交（导致1X015失败）

**代码位置：** `follow_engine.py:3918-3937`

**问题1：初始参数来自后台订单**
```python
# 后台订单的水位（历史数据）
params.ioratio = str(order.get("odds") or "")
params.con, params.ratio = encode_handicap_line(...)  # 基于后台盘口线
```

**问题2：order_view返回最新水位，但不一定采用**
```python
# 只有在"盘口线一致"时才采用order_view的ioratio
if overrides.get("ioratio"):
    if abs(float(cur_line_lv) - float(want_line_lv)) < 1e-6:
        params.ioratio = overrides["ioratio"]  # 采用最新水位
    else:
        # 盘口线不一致时，不采用order_view的ioratio
        # 继续用后台的历史水位 ← 这里就是问题！
```

**后果：**
- 用历史水位去下注 → 会员端返回 `1X015`（让球数/赔率/比分已更新）
- 触发重试 → 再次查找盘口线 → 再次耗时10-30秒
- 循环往复，最终可能失败或者超时

### 5. 找不到实时水位导致失败（76.60%的真失败原因）

**数据来源：** 《跟单报错统计与优化方案.md》

**真失败原因 Top 1：**
```
盘口已变化 → 找不到目标盘口线: 144单 / 76.60%
```

**代码逻辑：**
```python
# 找不到原盘口线时
if not found:
    if wait_line_not_found_max_seconds > 0.0:
        # 进入等待探测模式（默认30秒）
        res["message"] = f"目标盘口线暂时找不到，正在重试 err=LINE_NOT_FOUND"
    else:
        # 直接停止该订单跟单
        res["message"] = f"当前盘口已变化，未在附加盘口中找到目标盘口线，已停止该订单跟单。"
        return res
```

**问题：**
- 主盘口线变化后，引擎会尝试在附加盘口中找回原盘口线
- 如果附加盘口也没有（盘口线确实消失了），就会停止跟单
- **76.60%的真失败**都是因为找不到原盘口线

**根本原因：**
- 引擎默认策略是"**只跟原盘口线，找不到就停止**"
- 而不是"**原盘口线消失了，就跟最新的盘口线**"

## 📊 二、性能数据量化分析

### 2.1 单个订单的处理耗时分解

基于代码分析和日志数据，一个**正常跟单**的耗时分解：

| 步骤 | 耗时（秒） | 说明 |
|------|-----------|------|
| **1. 入队等待** | 0-120+ | 取决于队列中有多少订单在排队 |
| **2. 会员选择** | 0.1 | 从弹药库中随机选择可用会员 |
| **3. order_view（预校验）** | 0.5-2 | 网络请求 + 解析XML |
| **4. 盘口线变化时查找** | 0-30 | 如果盘口线一致则跳过；否则触发复杂查找 |
| **5. FT_bet（真实下注）** | 0.5-2 | 网络请求 + 解析XML |
| **6. 结果记录 + TG通知** | 0.5-1 | 写入jsonl + 发送Telegram |
| **7. 分单延迟（2-4次）** | 120-360 | split_count=3时，等待2×120=240秒 |
| **总耗时（单笔）** | **1-35秒** | 不含分单延迟 |
| **总耗时（3分单）** | **241-395秒** | 含分单延迟 |

### 2.2 失败重试的耗时累加

**场景：盘口线变化导致1X015**

| 次数 | 操作 | 耗时（秒） | 累计耗时 |
|------|------|-----------|---------|
| 第1次 | order_view + 盘口线查找 + FT_bet → 1X015 | 15-35 | 15-35 |
| 第2次 | order_view + 盘口线查找 + FT_bet → 1X015 | 15-35 | 30-70 |
| 第3次 | order_view + 盘口线查找 + FT_bet → 1X015 | 15-35 | 45-105 |
| 第4次 | order_view + 盘口线查找 + FT_bet → 1X015 | 15-35 | 60-140 |
| 第5次 | order_view + 盘口线查找 + FT_bet → **成功** | 15-35 | **75-175** |

**结论：**
- 一个订单从开始到成功，可能耗时 **75-175 秒**（1.2-3分钟）
- 在这期间，队列中的其他订单全部等待
- 如果是分单场景，再加上 240 秒分单延迟 = **315-415 秒**（5-7分钟）

### 2.3 队列阻塞的雪崩效应

**假设场景：**
- 队列中有10个订单（A、B、C、D、E、F、G、H、I、J）
- `queue_max_per_tick = 3`（每轮循环最多处理3个）
- `split_delay_seconds = 120`（分单延迟120秒）

**时间线推演：**

```
T=0s:    订单A开始处理（分3单）
T=15s:   订单A第1单成功，等待120秒
T=135s:  订单A第2单成功，等待120秒
T=255s:  订单A第3单成功，订单A完成
         订单B开始处理
T=270s:  订单B成功（单笔）
         订单C开始处理
T=285s:  订单C成功（单笔）
         ← 第1轮循环结束，处理了3个订单（A、B、C）

T=285s:  第2轮循环开始
         订单D开始处理（分3单）
T=300s:  订单D第1单成功，等待120秒
T=420s:  订单D第2单成功，等待120秒
T=540s:  订单D第3单成功，订单D完成
         订单E开始处理
T=555s:  订单E成功（单笔）
         订单F开始处理
T=570s:  订单F成功（单笔）
         ← 第2轮循环结束

总耗时：570秒（9.5分钟）处理了6个订单
订单G、H、I、J 还在等待...
```

**结论：**
- **订单J需要等待超过10分钟才能开始处理**
- 在滚球场景下，10分钟后盘口早已关闭或者比分变化
- 这就是用户看到的"**多单没跟上拖慢整个队伍**"的现象

## 🎯 三、根本原因总结

### 问题1：是不是每次提交跟单失败一次都会去傻傻的等待？

**答：以前是，现在不是了。**

**代码证据：** `follow_engine.py:5896-5910`
```python
else:
    # 你的要求：一旦报错（已有失败记录），不要再等 retry_delay_seconds（例如 6 秒），
    # 立即让出队列去处理下一单；本单在下一轮循环中尽快再尝试（由 last_attempted_at 保证公平轮转）。
    job.next_try_at = float(now_ts())
    print(
        f"[{now_iso()}] 跟单失败(让出队列，立即重试) member={result.get('member')} order={job.order_id} attempt={job.attempts} msg={job.last_message}",
        flush=True,
    )
```

**但仍然存在的等待：**
1. **分单延迟**：每笔分单之间等待 `split_delay_seconds`（当前120秒）
2. **1X001 封盘等待**：等待 `wait_1X001_probe_seconds`（8秒）× N次，最长120秒
3. **LINE_NOT_FOUND 等待**：等待 `wait_line_not_found_probe_seconds`（2秒）× N次，最长30秒

---

### 问题2：是不是拿历史的水位去提交的？

**答：是的，存在这个问题。**

**证据1：初始参数来自后台订单**
```python
# follow_engine.py 中构建BetParams时
params.ioratio = str(order.get("odds") or "")  # 后台订单的历史水位
```

**证据2：盘口线不一致时，不采用order_view的最新水位**
```python
# follow_engine.py:3918-3937
if overrides.get("ioratio"):
    # 只有盘口线一致时才采用
    if abs(float(cur_line_lv) - float(want_line_lv)) < 1e-6:
        params.ioratio = overrides["ioratio"]  # 采用最新
    # 否则继续用后台的历史水位
```

**后果：**
- 用历史水位下注 → 1X015（让球数/赔率已更新）
- 触发重试 → 重新查找 → 再次失败
- **这是导致1X015高发（15.67%）的主要原因**

---

### 问题3：是不是找不到实时的水位导致的跟不上单？

**答：是的，这是76.60%真失败的主要原因。**

**数据证明：**
```
真失败原因 Top 1：
盘口已变化 → 找不到目标盘口线: 144单 / 76.60%
```

**问题根源：**
1. **引擎策略过于严格**：只跟原盘口线，找不到就停止
2. **查找逻辑过于复杂**：调用多个接口、遍历多个showtype/wtype/p3type
3. **查找耗时过长**：单次查找10-30秒，这期间盘口可能再次变化
4. **分单耗时累加**：第2/3单查找时，盘口已经变化多次

## 🚀 四、优化方案（按优先级）

### Phase 1：立即优化（低风险、高收益）⭐⭐⭐

#### 1.1 大幅降低分单延迟

**当前配置：**
```json
"split_delay_seconds": 120.0  // 每笔120秒
```

**优化建议：**
```json
"split_delay_seconds": 0.5    // 降低到0.5秒
```

**收益：**
- 3分单总耗时：从 240秒 → **1秒**（提速 240倍）
- 队列吞吐量：从 6单/9.5分钟 → 6单/30秒（提速 19倍）
- **真失败率预计下降 30-50%**（因为减少了"分单期间盘口变化"的窗口）

**风险：**
- 极低。分单间隔0.5秒已经足够避免"同时下注冲突"
- 原来120秒的延迟过于保守，没有必要

---

#### 1.2 提高队列并发度

**当前配置：**
```json
"queue_max_per_tick": 3  // 默认值
```

**优化建议：**
```json
"queue_max_per_tick": 10  // 提高到10
```

**收益：**
- 每轮循环处理订单数：从 3个 → 10个（提速 3.3倍）
- 订单J的等待时间：从 10分钟 → 3分钟
- 队列响应速度明显提升

**风险：**
- 中等。可能增加服务器压力（10个并发请求）
- 建议：先提高到5-8，观察稳定性后再提高到10

---

#### 1.3 优化1X015/1X016快速重试策略

**当前问题：**
- 遇到1X015时，会走完整的盘口线查找逻辑（10-30秒）
- 然后再重试

**优化建议：**
```python
# 在收到1X015时，立即用order_view返回的最新水位重试
# 不要走复杂的盘口线查找逻辑

if err == "1X015" or err == "1X016":
    # 立即从order_view获取最新水位
    ov_latest, _ = member_order_view(...)
    if ov_latest:
        params.ioratio = ov_latest.get("ioratio")
        params.con = ov_latest.get("con")
        params.ratio = ov_latest.get("ratio")
        # 立即重试，不要sleep
        continue
```

**收益：**
- 1X015重试耗时：从 10-30秒 → **0.5-2秒**（提速 10-30倍）
- 1X015成功率预计提升 50-80%

**风险：**
- 低。只是改变了重试策略，不影响其他逻辑

---

### Phase 2：中期优化（中风险、高收益）⭐⭐

#### 2.1 改进盘口线查找策略（放宽容忍度）

**当前策略：**
- 只跟原盘口线，找不到就停止（76.60%的失败原因）

**优化策略1：允许跟最新盘口线（激进）**
```json
"allow_line_change": true  // 允许盘口线变化
```

**优化策略2：优先找原盘口线，找不到则跟最新（折中）**
```python
# 在try_refresh_*函数中
if not found:
    # 找不到原盘口线
    if is_total_market:  # 大小盘
        # 已经在代码中实现了：回退到order_view的最新盘口线
        params.con = overrides.get("con")
        params.ratio = overrides.get("ratio")
        params.ioratio = overrides.get("ioratio")
        return True  # 继续跟单
    else:  # 让球盘
        # 新增：允许跟最新盘口线（当前代码会直接停止）
        params.con = overrides.get("con")
        params.ratio = overrides.get("ratio")
        params.ioratio = overrides.get("ioratio")
        return True  # 继续跟单
```

**收益：**
- **真失败率预计下降 50-70%**（76.60% → 20-30%）
- 跟单成功率大幅提升

**风险：**
- 中等。可能会跟到"不同盘口线"的单
- 建议：先在配置中增加开关，让用户选择是否允许

---

#### 2.2 简化盘口线查找逻辑（减少接口调用）

**当前问题：**
- 查找一次盘口线，可能调用10+个接口，耗时10-30秒

**优化建议：**
```python
# 1. 减少showtype遍历
showtype_candidates = [showtype]  # 只查当前showtype，不遍历hot/today/early

# 2. 减少wtype遍历
candidates = candidates[:2]  # 只查前2个候选wtype

# 3. 跳过page_count（耗时且命中率低）
# 直接用固定的p3type列表：["MAIN", "MOUA"]

# 4. 使用缓存
# 对于同一个gid，缓存lid/ecid（已实现）
# 对于同一个gid+wtype，缓存盘口线查找结果（新增）
```

**收益：**
- 盘口线查找耗时：从 10-30秒 → **2-5秒**（提速 5-10倍）
- 队列吞吐量提升 2-3倍

**风险：**
- 中等。可能降低"找到原盘口线"的成功率
- 建议：先在配置中增加 `quick_mode` 开关

---

#### 2.3 引入并发下注（多线程/协程）

**当前问题：**
- 单线程串行处理队列
- 一个订单卡住，后面所有订单等待

**优化建议：**
```python
# 使用线程池并发处理多个订单
from concurrent.futures import ThreadPoolExecutor

executor = ThreadPoolExecutor(max_workers=5)

for job in ready_jobs[:10]:  # 取前10个待处理订单
    # 并发提交到线程池
    future = executor.submit(process_job, job)
    futures.append(future)

# 等待所有任务完成
for future in futures:
    result = future.result(timeout=30)
```

**收益：**
- 队列吞吐量提升 **5-10倍**
- 订单等待时间大幅降低

**风险：**
- 高。多线程可能引入并发问题（状态冲突、重复下注）
- 建议：先用协程（asyncio）实现，风险较低

---

### Phase 3：长期优化（高风险、高收益）⭐

#### 3.1 拆分跟单引擎为多个独立服务

**架构重构：**
```
当前架构：
  follow_engine.py (单线程、串行处理)
    ↓
  处理所有订单

优化架构：
  订单调度器 (Scheduler)
    ↓
  分发到多个 Worker
    ├── Worker 1 (处理订单A、B、C)
    ├── Worker 2 (处理订单D、E、F)
    ├── Worker 3 (处理订单G、H、I)
    └── Worker 4 (处理订单J、K、L)
```

**收益：**
- 真正的并发处理
- 队列吞吐量提升 **10-50倍**

**风险：**
- 极高。需要大规模重构
- 建议：作为长期规划

---

#### 3.2 智能水位追踪（Machine Learning）

**思路：**
- 使用机器学习模型预测"盘口线何时会变化"
- 提前刷新水位，减少1X015失败

**收益：**
- 1X015失败率下降 70-90%

**风险：**
- 极高。需要大量数据训练模型
- 建议：作为长期规划

跳过复杂的盘口线查找逻辑。

app/follow_engine.py

【修改位置】
在 place_bet 函数中，bet接口返回1X015/1X016后的处理逻辑（约4400-4500行）

【当前逻辑】
```python
# 当前代码（简化）
if err == "1X015" or err == "betError000":
    # 走完整的盘口线查找（耗时10-30秒）
    ok, used_wt, msg = try_refresh_handicap_odds_via_game_more(...)
    if ok:
        # 重试
        continue
```

【优化后逻辑】
```python
if err == "1X015" or err == "1X016" or err == "betError000":
    # 策略1：直接用order_view的最新水位（最快）
    if overrides.get("ioratio") and overrides.get("con") and overrides.get("ratio"):
        params.ioratio = overrides["ioratio"]
        params.con = overrides["con"]
        params.ratio = overrides["ratio"]
        # 立即重试，不sleep
        try:
            time.sleep(float(fast_retry_bet_error_delay))  # 默认0.2秒
        except Exception:
            pass
        continue

    # 策略2：如果order_view的水位为空，才走盘口线查找
    ok, used_wt, msg = try_refresh_handicap_odds_via_game_more(...)
    if ok:
        try:
            time.sleep(float(fast_retry_bet_error_delay))
        except Exception:
            pass
        continue
```

【关键点】
1. 优先使用order_view返回的最新水位（已经在之前的逻辑中获取并存储在overrides中）
2. 只有在order_view没有返回水位时，才走复杂的盘口线查找
3. 快速重试间隔：0.2秒（已有配置：fast_retry_betError_delay_seconds）

【验证】
1. 模拟盘口线变化场景（手动修改order_view返回的水位）
2. 观察日志中的"跟单失败(让出队列，立即重试)"消息
3. 确认重试耗时从10-30秒降低到1秒以内
4. 确认1X015的成功率明显提升

【预期收益】
- 1X015重试耗时：从 10-30秒 → 0.5-2秒（提速 10-30倍）
- 1X015成功率预计提升 50-80%
- 队列吞吐量提升 2-3倍

【风险】
低。只是改变了重试策略的优先级，不影响其他逻辑。
如果order_view的水位不准确，仍然会走原有的盘口线查找逻辑作为兜底。
